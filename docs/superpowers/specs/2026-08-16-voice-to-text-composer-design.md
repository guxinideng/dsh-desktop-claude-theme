# 输入框语音转文字设计

日期:2026-08-16
状态:已确认设计,待写实施计划

## 背景

dsh 移动端 UI 适配完成后(见 mobile.css / mobile.js 现有改动),composer 输入框只能靠手机键盘打字。用户希望能直接对着手机说话,转成文字填进输入框,自己看一眼/顺手改几个字,再手动点发送——不是"说完自动发出去",发送这一步始终由用户手动触发。

## 交互设计

- **触发手势**:按住麦克风按钮说话,松开结束——跟微信语音消息、大多数输入法自带的语音键一致的操作习惯,不容易误触,单手可操作。
- **确认方式**:转写完成的文字直接填进输入框(效果等同于手动打字打出来的),不额外弹确认框。看着没问题就点发送;识别错了几个字也能直接在输入框里改,不用学一套新操作。
- 麦克风按钮是新增的独立按钮,放在输入框操作区域内、跟发送按钮相邻。点击输入框本身的打字功能完全不受影响,两者并存。

## 技术方案:本地 whisper.cpp,跑在 Mac 上

### 排除的备选方案

- **浏览器原生 Web Speech API**:iOS Safari 从未实现 `SpeechRecognition` 接口,用户的实际使用场景(iPhone)跑不起来,直接排除。
- **讯飞云端 STT(录音文件转写大模型)**:另一个项目(bookkeeping-app)里已验证可用的方案,签名/接入方式见 `iflytek_stt` 记忆。技术上可行,但需要讯飞账户和密钥——密钥要么放前端(暴露在发给手机的网页源码里),要么放后端(remote-gateway.js 代多一层网络调用)。
- **VPS 上跑本地模型**:VPS 实测配置是 1 核 CPU、约 1GB 内存、无 GPU,跑不动任何有实用准确率的语音模型,而且会跟 VPS 现有的隧道转发职责抢占本就紧张的资源,风险大于收益。

### 选定方案的依据

用户的 Mac(Apple M5 芯片、16GB 内存)算力远超 VPS,且已经具备大半基础设施:

- Homebrew 已装 `whisper-cpp` 1.9.1(提供 `whisper-cli` 命令行工具),Metal GPU 加速在这台机器上实测正常工作
- Homebrew 已装 `ffmpeg`
- 只缺一个真正可用的模型文件(此前用户用过的 VoiceInk App 遗留的归档目录里只有 whisper.cpp 自带的测试占位模型,体积几百 KB,不能实际使用,需要重新下载)

相比讯飞云端方案:不需要注册账户或管理密钥、音频不出本机、不依赖外部服务可用性或额度。代价是 Mac 必须保持开机且 remote-gateway.js 常驻运行——这本来就是整套远程访问架构的前提(dsh 本身也要求 Mac 常驻),不算新增负担。

## 整体数据流

```
手机浏览器
  │ 按住麦克风按钮说话,松开
  │ MediaRecorder 录一段音频
  ▼
mobile.js
  │ fetch POST 音频到 /__ds_theme/stt(鉴权复用现有 cookie 机制)
  ▼
remote-gateway.js(新路由)
  │ 1. 音频写入临时文件
  │ 2. ffmpeg 转成 16kHz 单声道 wav
  │ 3. spawn whisper-cli 跑推理
  │ 4. 删除临时文件
  │ 5. 返回 { text: "..." }
  ▼
mobile.js
  │ 文字填入输入框(不自动发送)
```

`/__ds_theme/stt` 这个新路由插在现有请求处理流程里"THEME_ASSETS 静态资源判断"之后、"转发给 dsh 本体(`proxy.web`)"之前——它是网关自己独立处理、代答的请求,既不需要等 `ensureDshReady()`,也不转发给 dsh,跟现有 `serveThemeAsset` 属于同一层级的职责。

## 详细设计

### 前端(mobile.js / mobile.css)

- composer 输入框操作区域新增一个麦克风图标按钮,是真正的 `<button>` 元素——会自动落入现有拖拽手势的排除列表(`button, a, [role="button"], [role="menuitem"]`),不会被侧边栏横滑手势误吞,这是复用已经踩过坑、验证过的机制。
- 状态机:
  - **待机**:显示麦克风图标
  - **按住录音中**:图标变色(如变红)+ 简单的脉动动画反馈"正在录"
  - **松开后识别中**:小 loading 状态,文字提示"识别中..."
  - **完成**:文字落入输入框,回到待机状态
  - **失败**:短暂的错误提示(见下方"边界情况"),回到待机状态
- 首次使用会触发系统麦克风权限弹窗(`getUserMedia`)。网关本身已是 HTTPS,不会遇到浏览器因不安全上下文而拒绝该权限请求的问题。

### 后端(remote-gateway.js)

- 新增 `POST /__ds_theme/stt`,请求体是音频二进制数据
- `whisper-cli` 可执行文件路径、模型文件路径通过环境变量配置(风格上与现有 `TLS_CERT_FILE`/`TLS_KEY_FILE` 等一致),不写死路径
- 设置调用超时上限(建议 30 秒),防止单次调用异常卡死占用资源
- 临时文件的写入与清理用 try/finally 包裹,确保异常路径也不留垃圾文件
- 复用现有 `authMethod()` 鉴权逻辑,不引入新的鉴权或密钥管理机制

### 模型选择

推荐 whisper `large-v3-turbo` 的量化版本——比 `medium` 精度更好,且专门优化过推理速度,在这台 M5 + GPU 加速的机器上速度不是瓶颈。需要用 whisper.cpp 官方提供的下载脚本获取一次(几百 MB),一次性操作。

## 边界情况与错误处理

| 情况 | 处理方式 |
|---|---|
| 麦克风权限被拒绝 | 提示用户去系统设置开启权限 |
| 按住时长过短(如 <0.3 秒,可能是误触) | 直接忽略,不触发上传 |
| 识别结果为空(没说话/声音太小) | 提示"没听清,再试一次",不把空文字填入输入框 |
| 网络请求失败或 whisper 调用出错 | 短暂错误提示,不影响手动打字这条路径 |

## 明确不做的(out of scope)

- 不做实时流式字幕——松手后才转写,不是边说边出字
- 不做语言/模型切换 UI——固定用多语言模型,中文场景够用
- 不做录音历史或回放功能
